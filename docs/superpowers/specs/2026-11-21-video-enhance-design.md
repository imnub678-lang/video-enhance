# 影片畫質增強工具 — 設計文件

日期：2026-11-21
狀態：待核准

## 1. 意圖

做一個本機執行的桌面工具：拖入影片，輸出「真超分（1080p → 4K）＋ 補幀（→ 60fps）」的成片。

使用者動機：現有線上工具要麼是假超分（bicubic 放大加銳化），要麼是雲端付費且限片長；剪映的 4K 導出同樣只是編碼層放大。要一個不傳雲端、不限片長、能自己調的本地方案。

## 2. 目標

- G1 真超分：用神經網路重建細節，輸出 3840×2160
- G2 補幀：任意來源幀率 → 60fps，用光流／深度模型插幀
- G3 桌面 GUI：拖放、預設選擇、進度、可中止
- G4 音訊原樣直通（`-c:a copy`），內封字幕保留
- G5 輸出到 `D:\AI視頻完成品\`，命名 `主題_副題.mp4`
- G6 全部本機執行，無網路依賴（模型一次性下載除外）

## 3. 非目標

- 不做雲端上傳、不做多用戶、不做帳號
- 不做剪輯功能（剪切、轉場、字幕編輯）
- 不做串流即時增強（離線批次處理）
- 第一版不做 TensorRT 加速、不做 INT8 量化
- 不做自建模型蒸餾訓練
- 不處理 8K 輸出

## 4. 反目標（即使技術上跑得通也算失敗）

- 用 bicubic／lanczos 冒充超分
- 輸出檔案比原片大一倍但看不出差別
- GUI 卡死（推論必須在子進程，不得阻塞主執行緒）
- 音畫不同步
- 顯存溢出導致中途崩潰且無恢復

## 6. 方案比較

### 方案 A：包一層現成工具（Video2X／Waifu2x-Extension 命令列）
優點：兩三天可交付。缺點：受制於它們的參數與 bug，無法做自訂預設與進度回報，後續改不動。否決。

### 方案 B：ComfyUI 工作流（VHS 節點逐幀）
優點：零開發，模型現成。缺點：逐幀落盤再讀回，I/O 成為瓶頸；無批次佇列；4K 幀序列佔數百 GB。否決。

### 方案 C：自建管線（採用）
Python 管線，ffmpeg 解碼 → 記憶體張量 → 超分 → 補幀 → ffmpeg NVENC 編碼，PySide6 做外殼。
優點：全程管線化不落盤、可自訂預設、可中止續跑、可逐步加 TensorRT。
缺點：要自己實作模型載入與管線編排，開發量最大。

**選 C。** 前兩案都無法滿足 G2（任意幀率 → 60fps）與 G3（進度／中止）。

## 7. 架構

```
┌──────────────── GUI (PySide6, 主進程) ────────────────┐
│ 拖放區 · 預設選擇 · 輸出設定 · 進度條 · 日誌 · 中止   │
└────────────────────┬─────────────────────────────────┘
                     │ QProcess（子進程，可 kill）
┌────────────────────▼─────────────────────────────────┐
│              worker.py（單一任務執行器）              │
│                                                       │
│  ffmpeg 解碼 pipe ──► 幀緩衝 ──► 超分 ──► 補幀 ──► 編碼 pipe │
│   (rawvideo bgr24)   (deque)   (SR module) (RIFE)  (hevc_nvenc) │
│                                                       │
│  進度：已處理幀數 / 總幀數 → stderr JSON → GUI        │
└───────────────────────────────────────────────────────┘
```

### 模組

| 檔案 | 職責 |
|---|---|
| `app/main.py` | GUI 入口，Qt 介面 |
| `app/worker.py` | 任務執行器，被 QProcess 呼叫 |
| `engine/decode.py` | 啟動 ffmpeg 解碼子進程，讀 rawvideo |
| `engine/encode.py` | 啟動 ffmpeg 編碼子進程，寫 rawvideo，mux 原音軌 |
| `engine/sr.py` | 超分模型載入與分塊推論 |
| `engine/fi.py` | RIFE 補幀，任意 timestep |
| `engine/pipeline.py` | 串接上述，管理緩衝與時間戳 |
| `engine/models.py` | 模型下載、快取、校驗 |
| `presets/*.json` | 預設參數 |

### 資料流

1. `ffprobe` 取時長、幀率、解析度、是否有內封字幕
2. ffmpeg 解碼 → stdout 吐 `bgr24` 原始幀，Python 逐幀讀
3. 每幀進超分（必要時分塊）→ 得到 3840×2160 幀
4. 補幀模組按目標時間戳在相鄰幀間插值，輸出 60fps 序列
5. 寫入編碼 ffmpeg stdin → `hevc_nvenc`（可切 `libx265` 高質量）→ 音軌 `-c:a copy`、字幕 `-c:s copy`
6. 輸出至指定路徑

## 8. 關鍵技術決策

### D1 超分模型：Real-ESRGAN 官方輕量版
- `realesr-general-x4v3`（約 5 MB，SRVGGNetCompact 架構）：通用，含可調降噪強度
- `realesr-animevideov3`（約 2.4 MB）：動漫／線條類

理由：官方蒸餾版，比 `RealESRGAN_x4plus` 快 3-5 倍，影片場景細節損失不可見。12 GB 顯存跑得動。

1080p → 4K 的路徑：x4 推到 4320p，再 area 降採到 2160p（過採樣，邊緣更銳）。

快速模式不換模型，只降 tile 大小與編碼參數。**不引入 RealCUGAN**：少一個架構、少一組權重、少一條下載路徑，性價比不足。

### D2 不裝 basicsr
自行實作 `SRVGGNetCompact` 與 `RRDBNet` 的網路定義（各約 40 行）。理由：`basicsr` 依賴 `torchvision.transforms.functional_tensor`，新版 torchvision 已移除，是已知的安裝地雷。自寫架構可直接 `torch.load` 官方權重。

### D3 補幀：RIFE
`rife46` 權重（約 20 MB），IFNet 架構。支援任意 timestep，因此 24fps → 60fps 直接按目標時間戳插值，不需整數倍。

備援：若 PyTorch 版在某版本算子不兼容，改用 `rife-ncnn-vulkan` 獨立 exe（無 Python 依賴）。

### D4 環境：獨立 venv
`D:\video-enhance\.venv`，Python 3.13.14，安裝 `torch==2.14.1+cu130`、`PySide6`、`opencv-python`、`av`、`numpy`。

理由：不污染 ComfyUI 環境（ComfyUI 更新可能升／降 torch 版本，會連帶打壞本工具）。代價是首次下載約 3-4 GB。

否決的替代：直接用 `D:\ComfyUI\.venv`（省 3 GB 下載，但耦合風險高，且 PySide6 裝進去會影響 ComfyUI 啟動速度）。

### D5 顯存控制
4K 超分必須分塊：`tile=512`、`tile_pad=16`，逐塊推論後拼接。分塊大小依顯存自動降級（512 → 384 → 256）。

### D6 進度與中止
worker 以 JSON 行寫 stderr（`{"stage":"sr","done":120,"total":240}`），GUI 解析。中止時 GUI kill QProcess 樹，刪除半成品。

### D7 編碼
預設 `hevc_nvenc -preset p5 -cq 19`；提供「高質量」選項切 `libx265 -crf 18`（慢約 5 倍）。
像素格式 `yuv420p10le` 保留 10 bit 位深，避免 8 bit 帶狀。

## 9. 預設

| 預設 | 超分 | 補幀 | 編碼 | 實測耗時（7 秒 1080p24 → 4K60） |
|---|---|---|---|---|
| 高質量 | x4 過採樣降採 | RIFE x2.5 | libx265 crf18 | 未實測（估 2 倍於平衡） |
| 平衡（默認） | x4 過採樣降採 | RIFE x2.5 | hevc_nvenc cq19 | 約 230 秒 |
| 快速 | x4 過採樣降採（tile 768） | RIFE x2.5 | hevc_nvenc cq21 | 229.6 秒 |
| 只補幀 | 無 | RIFE | 同平衡 | 未實測（估 30-40 秒） |
| 只超分 | 同平衡 | 無 | 同平衡 | 未實測（估 90-120 秒） |

實測條件（2026-11-21）：RTX 5070 Ti Laptop 12 GB，`晨霧森林_FPV穿越溪谷.mp4` 切 7 秒轉 24fps，FP16 推論，tile 768。峰值顯存 729 MB。

**TensorRT 加速（第二期提前實作）**：SR 與 RIFE 都編譯成固定形狀的 TRT 引擎並快取到 `models/trt_cache/`（SRVGG 800×800 引擎 15 MB，RIFE 2176×3840 引擎 363 MB），載入 0.04 秒。

| 版本 | 7 秒素材耗時 | 換算 10 秒 |
|---|---|---|
| 純 PyTorch FP16 | 229.6 秒 | 約 5.5 分鐘 |
| TRT 引擎 + 全程 GPU 張量 | **100.6 秒** | **約 2.4 分鐘** |

關鍵發現：只換 TRT 引擎而不管資料搬運，整體只快 4%（219.5 秒）——算力紅利全被 CPU↔GPU 的 numpy 轉換吃掉。改成全程張量（解碼後轉一次、編碼前轉一次）才拿到 2.28 倍。

品質驗證：TRT 版與 PyTorch 版同一幀的像素平均差 0.43／255，銳度指標 28.8 vs 28.3。

60 秒素材約 14 分鐘。

**真實素材實測（1440p 10-bit）**：`剪映完成品\11月15日-副本.mp4`，2560×1440 60fps 10-bit，9.62 秒 / 576 幀 → 4K60，耗時 197.9 秒（20.6 倍實時），峰值顯存 889 MB，輸出 27.3 MB。因為來源已是 60fps，實際只跑超分、未補幀。銳度指標 238.7 vs bicubic 31.5，髮絲與睫毛明顯更清楚，無過度銳化光暈。

## 10. 風險

| 風險 | 影響 | 對策 |
|---|---|---|
| torch 2.14 與 RIFE 原版算子不兼容 | 補幀跑不動 | 備援 `rife-ncnn-vulkan` exe |
| 4K 分塊接縫可見 | 畫面有格狀紋 | `tile_pad=16` 重疊裁切；提供 tile 大小可調 |
| 24→60fps 非整數倍插值出現抖動 | 動作不順 | 改用累積時間戳插值，非固定倍數 |
| 長片中途失敗 | 前功盡棄 | 第一版接受重跑，不做分段。分段拼接涉及 PTS 偏移與音訊對齊，複雜度不值 |
| NVENC 畫質不如 x265 | 高動態場景有塊 | 提供 x265 選項，默認 cq19 已足夠 |

## 11. 成功標準

1. 一段 10 秒 1080p 24fps 測試片，輸出游 3840×2160 60fps，可用播放器正常播放
2. 時長與原片一致（誤差 < 0.1 秒），音畫同步
3. 抽幀對比：輸出幀的細節明顯多於 bicubic 放大（不是銳化假象）
4. 補幀後無明顯鬼影或撕裂
5. GUI 全程不卡，進度條推進，中止按鈕有效
6. 峰值顯存 < 11 GB

## 12. 邊界情況決策（已核准）

| 情況 | 處理 |
|---|---|
| 輸入 ≤720p | x4 推到 2880p，再 area 降採到 2160p。仍為真超分 |
| 輸入 1080p | x4 推到 4320p，再降採到 2160p |
| 輸入 1080p～4K 之間 | 允許，仍走 x4 過採樣後降採到 2160p |
| 輸入 ≥4K | 拒絕，超分無意義 |
| 可變幀率（VFR） | 以 PTS 重採樣到固定 60fps，不假設等間隔 |
| 輸入 >60fps | 直接降採到 60fps，不插幀 |
| 輸入 =60fps | 跳過補幀，只做超分 |
| 內封字幕 | 僅 `mov_text` 可 `-c:s copy`；ASS／PGS 等放棄並記日誌，不燒錄 |
| 音軌 | 能 copy 就 copy；PCM／DTS／TrueHD 等 mp4 不支援的轉 AAC 192k |
| 10-bit SDR 輸入 | 允許（解碼轉 8-bit 處理，輸出仍為 10-bit） |
| HDR 輸入 | 拒絕，不做色調映射（第二期） |
| 命名 | GUI 兩個輸入框（主題／副題），預設從原檔名推導，可改 |
